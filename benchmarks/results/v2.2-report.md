## Method and host

- Runtime: build once, then 1 warmup and 7 timed runs per workload; the median is reported.
- Build: official mode - one lsaca build -r per repeat with a fresh LSACA_CACHE_DIR; the driver emits C with the default direct compiler backend, gcc 15.2.0 -O2 compiles the generated C and the cached runtime translation units, and the result is linked. The cached build re-uses the cache and only re-links.
- Scale runs: the same workload definition at small/medium/large sizes, 3 timed runs each with no warmup; arguments come from the oracle scale table.
- Peak memory: psapi GetProcessMemoryInfo PeakWorkingSetSize, polled while the process runs.
- Reference builds: C with gcc -O2, Rust with rustc -O; Python 3.14.4 and Node.js v24.14.1 run the idiomatic equivalent source. Every measured run is validated for byte-identical stdout and exit code 0 before timing.
- Host and toolchains are the ones listed under run identity above (12th Gen Intel(R) Core(TM) i7-1260P, 15.63 GiB, Windows 11). This is a single-machine, single-run measurement; see the fairness notes.

lsaca is faster than the C reference on 1 of 22 executed workloads (hashmap_string, 0.92x) and within 1.15x on 5, within 1.4x on 9, within 1.5x on 14.
Above 1.5x in this run: binary_trees (8.17x), string_build (6.83x), string_unicode (2.88x), string_split (2.00x), array_wordcount (1.79x), binary_trees_refs (1.77x), hashmap_wordcount (1.72x), hashmap_i64 (1.58x).

hashmap_string is the only workload where lsaca beats C: 227.5 ms vs 246.2 ms. The C reference uses a hand-written open-addressing map for this workload while lsaca's String hash map is the same implementation used by the other hash-map programs; the result is reported as a win, but it is a single workload and not a general claim.

The largest non-intentional gap is string_build (6.83x, 108.4 vs 15.9 ms): 1,000,000 format/push iterations, where per-token formatting and copying still dominate. string_unicode (2.88x) exercises the per-character API surface (chars, char_at, uppercase mapping), and string_split (2.00x) pays per-token String allocation. binary_trees (8.17x) is the by-value tree workload discussed above; binary_trees_refs (1.77x) shows the reference-based traversal is much closer to C.

Against Rust, lsaca is slower on most rows but faster on hashmap_wordcount (0.92x) and iterator_pipeline (0.98x); the Rust numbers are context, not a parity target, because the reference implementations differ in style.

The three ratio improvements that matter are the ones the 2.2 performance work targets:

- string_build 7.48x -> 6.83x (lsaca 97.2 -> 108.4 ms on a slower host, C 13.0 -> 15.9 ms). The 2.2 append path fuses push_str(&format!(...)) into the String append operation instead of formatting into a temporary and copying it, so the same 1,000,000-token loop does less allocation and copying work. The workload remains far slower than C, but the direction is the intended one and the absolute lsaca time grew less than the C reference.
- string_split 2.75x -> 2.00x (39.3 -> 25.9 ms, C 14.3 -> 12.9 ms): the same append fusion applies to the per-token push_str(&format!(...)) in this workload.
- binary_trees 11.05x -> 8.17x (212.5 -> 192.9 ms, C 19.2 -> 23.6 ms): the by-value tree workload is faster in absolute terms on a slower host, so the ratio improvement is real, but no 2.2 source edit or benchmark edit targets it directly; treat the mechanism as unexplained by this run and a candidate for a codegen profile rather than attributing it to a named change.

fib_iter's ratio drop (2.63x -> 1.15x) is partly a 2.1 side artifact: its 2.1 median (24.1 ms) was an outlier against 13-15 ms at the other scales of the same workload, while the 2.2 run measured 16.1 ms. The remaining ratio movements are consistent with the host difference and are not attributed to 2.2 language changes; on the hash-map rows the 2.2 stdlib get() is borrowed but still clones the lookup key internally, so String-keyed lookups pay one clone per call, which is a plausible contributor to hashmap_wordcount 1.50x -> 1.72x.

## What changed in 2.2.0 that touches these workloads

- Language: fixed-size arrays with index by usize, loop labels, lightweight lifetimes, From conversions with ?, and borrowed HashMap get/get_mut. None of these changes alter the benchmark algorithms.
- Performance: the String append path accepts &format!(...) as a call argument and fuses push_str(&format!(...)) into one append, removing the format-then-copy pattern that the 2.1 library surface forced on these sources.
- Benchmarks: the only 2.2 edit to the measured sources is the HashMap::get migration (map.get(k) becomes map.get(&k), with * where an owned value is needed). It changes no algorithmic work; the hash-map rows are discussed above.
- Nothing in the measured runtime path was removed or simplified: this report measures the same 22 programs at the same sizes as the 2.1 report.

## Validation

- 22 executed programs, each validated for byte-identical stdout and exit code 0 in every language before timing; all measured runs matched the expected checksum.
- Independent oracle verification: module scripts/oracles.py, 22 program oracles and 39 scale checksums (13 workloads x 3 scales), 0 mismatches.
- Harness warnings: none.
- Compile-only workloads (compile_large, modules_compile, package_compile) were built but not run; they are compile-time measurements only.

## Fairness notes and caveats

- Single machine, single run: medians of 7 runtime runs with 1 warmup after a fresh build.
- Compile time includes the whole official path: driver emit + gcc 15.2.0 -O2 on the generated C and the runtime translation units + link. C reference builds use gcc -O2; Rust uses rustc -O.
- The language implementations are not identical programs: Python and Node.js use the closest honest idiomatic form of each workload (often slower for different reasons); compare them only as context, not per-instruction.
- Peak memory is polled, not exact: Windows working-set sampling can miss short spikes.
- Short workloads (a few milliseconds) have a large relative noise floor; the C reference movement between the two runs is the scale of that effect.
- Ratios vs C are computed only where both languages ran the same workload; n/a elsewhere.
- Do not compare these numbers with measurements from another machine or another official run. This applies in particular to the 2.1 comparison: the host was slower during the 2.2 run, so use the ratio-to-C columns, not the millisecond columns, across versions.
