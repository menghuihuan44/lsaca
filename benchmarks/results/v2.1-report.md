## What changed and why

### Language and standard-library changes in 2.1.0 that touch these workloads

- Integer literals now default to i32 (previously i64). Benchmark sources annotate the values
  that need 64-bit arithmetic and use explicit suffixes where inference would narrow.
- Lengths, indices, capacities and counts are usize (Vec, String, slices, HashMap, iterators).
  Indexed accesses are written values[i as usize], and lengths that feed 64-bit arithmetic are
  converted with as i64.
- Read-only standard-library text parameters take &str; callers pass a literal directly or
  &string_var. String + String and += String are rejected; concatenation is String + &str or
  push_str.
- parse_i64 / parse_f64 return Result; std::env::var returns Result; file APIs return Result.

The v2.1 migration edited the benchmark sources mechanically - algorithmic work is unchanged.
The edits that appear in the measured files are:

- index conversions: values[left as usize], sorted[(n - 1) as usize];
- formatted output: let piece = format!("{},", v); s.push_str(&piece); because 2.1 rejects
  borrowing a temporary in push_str (E0745: cannot borrow a temporary value);
- text borrowing: push_str(&text) / String::from(x) + &suffix instead of String + String;
- explicit 64-bit annotations/suffixes where the new i32 literal default would overflow or
  change the inferred type (let mut total: i64, vec![0i64; n]).

### Attribution of the measured changes

string_build is the largest regression: 26.8 -> 97.2 ms (+263.0%). In 2.0 the token formatting was
fused into the String append path, so building the string did one append per token. In 2.1
push_str(&format!(...)) is rejected (a temporary cannot be borrowed) and String + String was
removed, so every token is formatted into a separate String and then copied into the
accumulator: one extra allocation and copy per iteration (1,000,000 tokens at the default
scale). This is a measured cost of the 2.1 library surface, not a regression in the string
primitive itself. The C reference moved +18.2% between the two runs.

Two other regressions are large enough to separate from noise. sort_i64 (+83.7%) and fib_iter (+79.9%)
cannot be costs of the source migration: fib_iter.ls was not edited in 2.1, and sort_i64.ls only
gained index casts that lower to no-ops. Their C references also moved (+7.3% and +25.3%), and both run
for only tens of milliseconds, so host load during this run is the most plausible explanation;
separating it from 2.1.0 code-generation changes needs a quiet-host rerun or a profile, and is
flagged as open. string_split (+61.3%) is the other >50% case; its migration uses the same
format-then-push pattern as string_build, so that mechanism may account for part of it.

The remaining regressions range from +10.7% to +28.8%; the C reference moved by up to +42.9% (string_unicode)
between the runs, so these deltas are within or near the observed noise:

- fib_memo: 10.5 -> 13.6 ms (+28.8%); C reference 9.7 -> 10.2 ms (+5.7%).
- sort_insertion: 11.4 -> 14.3 ms (+25.1%); C reference 8.9 -> 9.8 ms (+10.2%).
- loop_sum: 17.5 -> 20.6 ms (+17.7%); C reference 12.4 -> 13.4 ms (+7.7%).
- sieve: 32.9 -> 37.8 ms (+14.6%); C reference 29.6 -> 29.3 ms (-1.1%).
- string_unicode: 33.3 -> 38.1 ms (+14.3%); C reference 10.9 -> 15.6 ms (+42.9%).
- iterator_pipeline: 14.2 -> 16.0 ms (+12.7%); C reference 12.3 -> 12.2 ms (-0.3%).
- binary_trees: 190.7 -> 212.5 ms (+11.4%); C reference 18.5 -> 19.2 ms (+4.0%).
- vec_memory: 17.9 -> 19.9 ms (+10.7%); C reference 12.4 -> 14.5 ms (+16.8%).

Except for string_build (and possibly part of string_split), none of the v2.1 source migrations
adds or removes work on the hot path: the as usize conversions are no-ops after C lowering, and
the &str changes move a borrow at the call site rather than a copy in the loop. Code generation
and type representation changed substantially across the 2.1.0 release, so a codegen-level
profile on a quiet host is the right follow-up for these deltas, rather than attributing them
to the migration.

The improvements have the same caveat. The clearest are:

- binary_trees_refs: 59.5 -> 38.2 ms (-35.8%); C reference 25.5 -> 26.2 ms (+2.6%).
- fib: 31.4 -> 27.6 ms (-11.9%); C reference 23.8 -> 23.7 ms (-0.4%).
- matrix_multiply: 18.1 -> 16.2 ms (-10.8%); C reference 12.7 -> 12.7 ms (-0.1%).
- mandelbrot: 44.0 -> 39.5 ms (-10.1%); C reference 26.6 -> 31.7 ms (+19.3%).
- hashmap_wordcount: 36.0 -> 32.5 ms (-9.8%); C reference 25.2 -> 21.7 ms (-13.8%).
- hashmap_i64: 212.5 -> 196.3 ms (-7.6%); C reference 150.2 -> 145.6 ms (-3.0%).
- hashmap_string: 193.2 -> 181.8 ms (-5.9%); C reference 180.5 -> 163.5 ms (-9.4%).
- fn_pipeline: 12.7 -> 12.1 ms (-4.5%); C reference 9.1 -> 8.3 ms (-8.7%).

binary_trees stays an intentional exception: 212.5 ms, 11.05x C (v2.0: 10.31x C). The workload
builds and returns subtrees by value, so deep copies are part of the measured work by design;
binary_trees_refs is the reference-traversal variant of the same tree (38.2 ms vs C 26.2 ms).
Lowering the by-value cost would change the language semantics being measured, so the ratio is
documented rather than chased.

### Host variance

This is a single-machine measurement, and the two official runs were taken under different host
conditions. The C reference columns isolate that:

- string_unicode: C 10.9 -> 15.6 ms (+42.9%) while lsaca 33.3 -> 38.1 ms (+14.3%).
- fib_iter: C 7.3 -> 9.2 ms (+25.3%) while lsaca 13.4 -> 24.1 ms (+79.9%).
- mandelbrot: C 26.6 -> 31.7 ms (+19.3%) while lsaca 44.0 -> 39.5 ms (-10.1%).
- string_build: C 11.0 -> 13.0 ms (+18.2%) while lsaca 26.8 -> 97.2 ms (+263.0%).
- vec_memory: C 12.4 -> 14.5 ms (+16.8%) while lsaca 17.9 -> 19.9 ms (+10.7%).
- hashmap_wordcount: C 25.2 -> 21.7 ms (-13.8%) while lsaca 36.0 -> 32.5 ms (-9.8%).

Deltas smaller than the C movement on the same row should not be read as language changes.

## Fairness notes and caveats

- Single machine, single run: medians of 7 runtime runs with 1 warmup after a fresh build.
- Compile time includes the whole official path: driver emit + gcc 15.2.0 -O2 on the generated C
  and the runtime translation units + link. C reference builds use gcc -O2; Rust uses rustc -O.
- The language implementations are not identical programs: Python and Node.js use the closest
  honest idiomatic form of each workload (often slower for different reasons); compare them only
  as context, not per-instruction.
- Peak memory is polled, not exact: Windows working-set sampling can miss short spikes.
- Short workloads (a few milliseconds) have a large relative noise floor; the C reference movement
  between the two runs is the scale of the effect.
- Ratios vs C are computed only where both languages ran the same workload; n/a elsewhere.
- Do not compare these numbers with measurements from another machine or another official run.
