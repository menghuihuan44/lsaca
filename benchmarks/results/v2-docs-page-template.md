- `benchmarks/results/archive/v1.7/latest.json` - frozen copy of the published 1.7.0 run

## How to produce the report

The exact command line, preconditions, acceptance checks and post-run steps are in
`benchmarks/results/v2-official-run-plan.md`; this section is the short version.

    # 1. Lead: official run on an idle host (writes latest.json + latest.md; warnings must be []).
    python scripts/bench.py --compiler <absolute release lsaca.exe> --build-mode official

    # 2. Render the v2.0 sections from the new run plus both frozen baselines:
    #    archive/v1.7 (published 1.7 run) and archive/v2.0-pre-perf (Phase D baseline).
    python scripts/bench_report.py `
      --baseline benchmarks/results/archive/v1.7/latest.json `
      --baseline2 benchmarks/results/archive/v2.0-pre-perf/latest.json

    # 3. Paste the generated sections into the manual page as described below, then:
    python scripts/check_bench21.py        # 0 failures expected (more tables than before)
    python scripts/docs_verify.py          # docs-verifier's link/structure gate

`--compile-repeats 2` guidance for CI: CI and smoke jobs use `--quick` (which caps
compile repeats at 1) so they stay fast. When a CI-like run must report cold-build
medians rather than one cold sample, pass `--compile-repeats 2`; the published
official run keeps the default 3.

### Anomalies found in the baseline

1. **`string_unicode` is a genuine v2.0 regression: 375.0 ms (20.0x C), 13.4x its
   published v1.7 median (27.9 ms).** Isolated with phase probes (`p0`-`p7` under
   `target/migrator/probe/su_probes/`): the hotspot is `base.char_at(...)` - 1000 calls
   on a 120,000-char `String` cost ~270-300 ms over a build-only control. Root cause:
   the new external stdlib (`stdlib/src/string.ls`) implements `String::char_at` as
   `__str_char_at(self, index)`; the implicit `&String -> &str` coercion is lowered by
   `crates/lsaca/src/typeck/slices.rs:150-202` as a full-range slice, and
   `crates/lsaca/src/codegen/slices.rs:195-215` then makes **two owned heap copies**
   (`string_handle()` -> `ls_str_from_parts`, then `ls_str_substring` purely to validate
   the range) before the `str_char_at` arm at `:546-580` makes a **third** copy via
   `string_handle()`. Three 120 KB copies per call; the same pattern is in the
   `char_count`, `is_char_boundary`, `contains`/`starts_with`/`ends_with` and
   `to_uppercase`/`to_lowercase` arms. v1.7 had no stdlib wrappers (String methods were
   compiler builtins), hence the regression appeared with Phase B/C.
   Designed fix (codegen owner; not applied here): (A) skip the validation copies when
   the coercion is the full range (`start`/`end` both absent - it cannot fail), and
   (B) pass a stack `LsString { .len, .cap = len, .data }` view to read-only runtime
   observers instead of calling `string_handle()`. A prototype that bypasses the copies
   in the *generated C* restores the old performance: the full-workload probe drops
   from 284.5 ms to 31.6 ms (9.0x; ~1.7x C, i.e. back to the v1.7 level), checksum
   unchanged.
2. **`binary_trees` (by value) 545.3 ms / 18.76x C (29.47x on the large scale)** - a
   pre-existing deep-copy cost (v1.7 was 331.3 ms / 20.3x), not new; this is one of the
   Phase D targets (live-flag/deep-copy work in codegen).
3. Host-load caveat: `gcc` C compile medians are 0.27-0.56 s (v1.7: 0.21-0.29 s) and
   lsaca cold builds 2.1-2.7 s (v1.7: ~0.9-1.2 s); read the cold/cached columns as
   same-host directions, not targets. Cached medians are 42.8-68.7 ms against the
   ~15 ms target; `hashmap_i64` (1.29x C) and `hashmap_string` (1.49x C) are the
   workloads already closest to the target.
