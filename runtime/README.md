# lsaca C17 runtime

Portable C17 runtime for programs compiled by `lsaca`. Generated C links against
it, so the language's memory management (ORC: reference counting plus a cycle
collector), `String`, `Vec`, the builtin `HashMap` table, formatting, panics,
checked integer arithmetic, process information, file/directory/TCP/time/
environment I/O and math all behave the same on every supported platform.

The runtime is written carefully against the C17 standard: no compiler-specific
extensions, no VLAs, no GNU statement expressions, no threads, no third-party
code. It compiles warning-free with
`gcc -std=c17 -Wall -Wextra -Wpedantic` and with clang.

## Files

| File | Role |
| --- | --- |
| `lsaca_rt.h` | Public ABI. The only runtime header generated code includes. Frozen function signatures and frozen layouts of `LsString`, `LsVec_String`, `LsOpt_String`, `LsRes_String_String`, `LsMapTable`, `LsMapIter`. |
| `lsaca_rt_internal.h` | Private contract shared by the translation units (private allocation header layout, cross-unit helpers). Generated code never includes it. |
| `lsaca_rt.c` | Core: reference counted allocator, ORC cycle collector, leak report, panics, checked integer arithmetic, process helpers, math. |
| `lsaca_rt_string.c` | `LsString` objects: construction, copy-on-write mutation, search/transform, split, parse. |
| `lsaca_rt_vec.c` | Generic vector primitives and the frozen `LsVec_String` operations. |
| `lsaca_rt_fmt.c` | Format builder, shortest-round-trip float formatting, precision/width, Debug escaping, print helpers. |
| `lsaca_rt_map.c` | Builtin `HashMap` table: Swiss-table style open addressing (16-slot groups, H2 control bytes), tombstones, power-of-two growth, deterministic wyhash-style string hashing and bit-identical scalar fast paths, slot iteration. |
| `lsaca_rt_unicode.c` | Generated Unicode tables (case mapping, white space, Debug-escape categories) and the UTF-8 validation/scan primitives. Generated by `scripts/gen_unicode_tables.py`; the result is checked in, so building never runs Python. |
| `lsaca_rt_io.c` | Handle based operating-system I/O: file and directory handles, TCP sockets, wall-clock and monotonic time, sleep, calendar breakdown, environment variables and process arguments. Windows uses Win32 + Winsock2, POSIX uses POSIX.1-2008; the last error is per-thread. |
| `test/main.c` | Runtime self-test suite (`ALL CHECKS PASSED (10357 checks)`), including collector and collector-stress, refcount, panic-path, hash-map and hash-map-stress tests. |
| `test/io_tests.c` | Standalone I/O suite (`ALL CHECKS PASSED (298 checks)`): handle table, files, directories, rename/canonicalize, TCP loopback, time, environment variables and non-ASCII argument paths. |
| `test/bench_runtime.c` | Standalone micro-benchmark driver for the hot paths (not part of the smoke matrix). |
| `test/run_smoke.ps1` | Windows smoke-test driver (`SMOKE PASSED (121 checks)`): builds release/debug/leak-tracking configurations of the runtime and of the I/O suite, then exercises the panic/leak/IO/stdin/args child-process modes. |

`crates/lsaca/src/runtime.rs` embeds every file above (except the tests) with
`include_str!` and exposes `runtime::sources() -> &'static [(name, contents)]`.
The driver writes that complete list into every generated project; the CMake
project lists every translation unit. Adding a runtime file therefore only
requires adding it to that list, not touching codegen.

## Generated project

A generated project directory contains:

    main.c                  generated program
    CMakeLists.txt          generated CMake project
    lsaca_rt.h              public runtime header
    lsaca_rt_internal.h     private header (needed by the runtime .c files)
    lsaca_rt_unicode.h      private Unicode helper header
    lsaca_rt.c
    lsaca_rt_string.c
    lsaca_rt_vec.c
    lsaca_rt_fmt.c
    lsaca_rt_map.c
    lsaca_rt_unicode.c
    lsaca_rt_io.c

Build configurations:

| Configuration | Compiler flags |
| --- | --- |
| Release | `-std=c17 -O2 -DNDEBUG -Wall -Wextra` |
| Debug | `-std=c17 -O0 -g -DLSACA_DEBUG -Wall -Wextra` |
| Debug with leak tracking | additionally `-DLSACA_DEBUG_RC` (or alone) |

The runtime must be compiled with the same `-DLSACA_DEBUG`/`-DLSACA_DEBUG_RC`
choice as generated `main.c`: the leak report is part of the runtime, the
checked-arithmetic calls are emitted by codegen.

Build by hand (POSIX shell, from the generated directory):

    gcc -std=c17 -O2 -DNDEBUG -Wall -Wextra main.c \
        lsaca_rt.c lsaca_rt_string.c lsaca_rt_vec.c lsaca_rt_fmt.c \
        lsaca_rt_map.c lsaca_rt_unicode.c lsaca_rt_io.c -lm -o program

On Windows add `-lws2_32` for the TCP socket API in `lsaca_rt_io.c`; POSIX needs
`-lm` only. The generated CMake project adds the platform link libraries itself.

## Memory model (ORC)

Every managed object is a single `malloc` block: a private header (reference
count, payload size, magic word, drop/trace callbacks, collector bookkeeping)
immediately followed by the payload itself. `ls_alloc(size)` returns a zeroed
payload with reference count 1; `ls_alloc_managed(size, drop, trace)` also
registers the payload with the cycle collector. The initial reference count is
always 1, so a freshly produced value is already owned by its producer.

- `ls_retain(obj)` increments the count and returns `obj`; NULL is a no-op.
- `ls_release(obj)` decrements the count, frees at zero; NULL is a no-op.
- `ls_refcount(obj)` reports the current count (0 for NULL).
- Only cycle-capable payloads (Rc cells, closure environments) are traced; the
  collector marks a traced object as a candidate when its count drops but stays
  above zero. When enough candidates accumulate, or on shutdown, trial deletion
  finds objects only reachable from garbage cycles and frees them.
- Strings, `Vec` data buffers and other unmanaged payloads are never collector
  candidates and pay no trace bookkeeping on release.
- Releasing an invalid or already released handle prints
  `lsaca: runtime error: release of an invalid or already released reference-counted object`
  to stderr and exits with status 101. Out-of-memory is fatal in the same style.
- The runtime is not thread safe because the language has no threads. The I/O
  handle table is the one exception: it is guarded by a small critical section,
  so handles cannot be corrupted if another library thread shares the process.

## Allocator behaviour (release builds)

Programs create and drop many short-lived payloads (every intermediate `String`,
`Vec` buffer and tree node). In release builds (`NDEBUG`, no leak tracking) the
allocator recycles freed blocks instead of returning every one to `malloc`:

- A block is one header plus payload. Its class is the total size rounded up to
  8 bytes; every total up to 512 bytes has its own free list. The class is stored
  in the header padding and the free-list link reuses the dead entry pointer, so
  the private header layout and the public ABI are unchanged.
- The pool retains at most 32 MiB of blocks. Blocks beyond that budget go
  straight to `free()`, and the whole pool is returned from `malloc` at shutdown,
  so a process that allocates hard and then goes quiet does not pin an unbounded
  amount of memory. Shell exit therefore ends with the same heap state as a pure
  malloc/free allocator, which keeps heap checkers and the debug leak report
  clean.
- A recycled block is re-initialized exactly like a fresh one (magic word,
  callbacks, refcount, state, zeroed payload), so pooling is not observable
  through the language or through stale handles of debug builds.
- Debug and leak-tracking builds do not pool at all: they keep the released
  block in the stale-handle quarantine instead, so use-after-release diagnostics
  still work.
- Two build switches exist for A/B work: `-DLS_RT_NO_POOLING` compiles the
  release runtime without free lists, and `-DLS_RT_POOL_UNMANAGED_ONLY` pools
  only payloads that own no managed children (the smoke harness uses
  `-DLS_RT_NO_POOLING` to prove behaviour is identical without pooling).
- `ls_release` has an inline fast path for untraced, dropless payloads (strings,
  vector buffers, plain structs): the block is destroyed in place without
  touching the cycle collector's worklist or candidate list.
- UTF-8 helpers take an ASCII fast path where the result is identical: counting
  characters, collecting `chars`, case mapping and trimming scan words at a
  time and use the byte paths when every byte is below 0x80; non-ASCII input
  keeps the full Unicode implementation.

## Frozen data representations

Generated code never redefines these; they live in `lsaca_rt.h`:

    typedef struct LsString {        /* opaque in generated code */
        size_t len;                  /* byte length (no NUL) */
        size_t cap;                  /* byte capacity of data */
        char* data;                  /* inline NUL-terminated bytes */
    } LsString;
    /* A String value is a handle: LsString* (one reference counted allocation). */

    typedef struct LsVec_String { size_t len; size_t cap; LsString** data; } LsVec_String;
    /* The vector owns one reference per element. */

    typedef struct LsOpt_String { int32_t tag; union { LsString* some; } u; } LsOpt_String;
    /* tag 0 = None, tag 1 = Some. */

    typedef struct LsRes_String_String { int32_t tag; union { LsString* ok; LsString* err; } u; } LsRes_String_String;
    /* tag 0 = Ok, tag 1 = Err. */

Generic `Vec<T>` is a by-value struct emitted by codegen
(`{ size_t len; size_t cap; T* data; }`); its buffer is a raw `malloc` array,
not reference counted. The codegen copy helper deep-copies buffer and elements;
the release helper releases owned elements and frees the buffer.

## Ownership cookbook (for generated code)

A String is always an owned `LsString*` handle unless it is a borrowed
parameter/field. Pass one reference in and take one reference out.

- Fresh value: `ls_str_new()`, `ls_str_cstr("text")`,
  `ls_str_from_parts(bytes, len)`, `ls_format_begin(hint)` etc. all return an
  owned handle (count 1).
- Copy a handle: `copy = (LsString*)ls_retain((void*)original);`.
- Drop a handle: `ls_release(handle);`.
- String mutators are copy-on-write and **consume the caller's reference**;
  they return the handle to keep:
  `s = ls_str_push_str(s, suffix);`, `s = ls_str_push_cstr(s, ",");`,
  `s = ls_str_push_char(s, 'x');`, `s = ls_str_clear(s);`.
  When the receiver is unique and has room the mutation happens in place;
  otherwise it detaches (allocates a new object, releases the old reference).
- Format builder: start with `acc = ls_format_begin(hint);` then chain the
  consumers and keep the final result:
  `acc = ls_fmt_i64(acc, value);`, `acc = ls_format_push_cstr(acc, ", ");`,
  `acc = ls_fmt_f64(acc, x);`, `acc = ls_format_push_char(acc, '\n');`.
- `Vec<T>` push / insert, with the inline fast path:

      /* good: one branch in the common (capacity available) case */
      ls_vec_push_bytes(&v.data, &v.len, &v.cap, &value, sizeof value);

      /* still supported, out-of-line helper with a safe aliasing slow path */
      ls_vec_insert_bytes(&v.data, &v.len, &v.cap, v.len, &value, sizeof value);

  Both grow geometrically (start 4, double) and handle a `value` that points
  into the vector buffer. `ls_vec_alloc(capacity, elem_size)` allocates an
  exact-capacity zeroed buffer (for `Vec::with_capacity`), `ls_vec_free_bytes`
  frees it.
- `Vec<String>` owns one reference per element: `ls_vec_string_push(v, s)`
  retains `s`, `ls_vec_string_get` retains into `*out`, `ls_vec_string_remove`/
  `pop` transfer ownership out, `ls_vec_string_clear` releases elements and
  keeps the buffer, `ls_vec_string_free` releases elements and the buffer.
- Option/Result: `LsOpt_String r = ls_opt_string_some(s);` moves the reference
  into the union; the inactive branch is initialized, so release exactly the
  active branch once. Same for `ls_res_string_ok` / `ls_res_string_err`.
- Printing: `ls_print(s)` / `ls_println(s)` / `ls_eprintln(s)` take a borrowed
  handle (they do not consume it) and flush after every call, so program output
  keeps its order when pipes interleave stdout and stderr.
- Program exit: `ls_exit(code)` flushes stdout/stderr and exits; generated
  `main` calls `ls_runtime_shutdown()` before returning normally.

## Hash maps (builtin `HashMap<K, V>`)

`HashMap` is a builtin table type. The runtime owns only the three slot
arrays; generated code embeds an `LsMapTable` by value in a managed
`LsMap_K_V` payload and never allocates the table itself:

    typedef struct LsMapTable {
        unsigned char* keys;      /* slot array, cap * key_size bytes   */
        unsigned char* values;    /* slot array, cap * value_size bytes */
        unsigned char* states;    /* 0 empty, 1 occupied, 2 tombstone   */
        size_t len;
        size_t cap;               /* power of two, 0 before first insert */
        size_t key_size;
        size_t value_size;
        uint64_t (*hash_key)(const void*);
        bool (*eq_key)(const void*, const void*);
        void (*copy_key)(void*, const void*);
        void (*drop_key)(void*);
        void (*copy_value)(void*, const void*);
        void (*drop_value)(void*);
    } LsMapTable;

Algorithm: open addressing with linear probing, power-of-two capacity: a 3/4
load factor and tombstones. The capacity starts at 8 with the first insert and
doubles when an insert would exceed the load factor. Hash values are
deterministic: FNV-1a 64 over the key bytes followed by the splitmix64
finalizer; `i64`/`u64`/`bool` hash their 64-bit value (`bool` as 0/1) through the
same finalizer, and `String` keys hash their bytes. There is no random seed.
Iteration walks slot indices in order, which is deterministic for a given
sequence of operations but is slot order, not insertion order.

Key types: `K` is `i64`, `u64`, `bool` or `String`. Codegen supplies six
callbacks: scalar keys use typed `memcpy`, a no-op drop and the matching
`ls_hash_*`/`ls_eq_*` pair; `String` keys use `ls_hash_string_slot` /
`ls_eq_string_slot` (content equality) with `ls_retain`/`ls_release` for the
copy/drop callbacks. Values use the generic codegen copy/drop helpers; managed
values are traced for the ORC cycle collector.

Ownership contract (generated code must follow it):

- `ls_map_insert()` adopts (moves) both incoming blobs. When the key already
  exists, the stored value is copied through `copy_value` into
  `out_old_value` (when non-NULL) before the slot is overwritten, and the
  caller's duplicate key is released through `drop_key`. The function returns
  true iff an old value was written out.
- `ls_map_remove()` moves the stored value bytes into `out_value` (or releases
  the value when `out_value` is NULL) and releases the stored key.
- `ls_map_clear()` releases every stored key and value but keeps capacity; the
  generated wrapper's drop helper then `free()`s `keys`, `values` and
  `states`. All three pointers are NULL before the first insert.
- `ls_map_get_ptr()` and `ls_map_iter_next()` return borrowed views valid until
  the next mutation. `copy_key` is only used by codegen for the `keys()`
  snapshot, and `copy_value` for `get()` and old-value outputs; the adoption
  path never copies.
- `ls_map_init()` requires all six callbacks non-NULL and non-zero key/value
  sizes. All operations are O(1) expected; only `insert` allocates, and only
  when the table grows (or on the first insert). The table is neither thread
  safe nor reentrant.

## Formatting

- `Display` of floats is the shortest round-trip decimal, always expanded
  (never exponent notation): `1.0` prints `1`, `-0.0` prints `-0`,
  `1e300` prints 301 digits.
- `Debug` of floats adds `.0` to integral values and switches to exponent
  notation when the decimal exponent is below -4 or at least 16
  (`1e15` -> `1000000000000000.0`, `1e16` -> `1e16`, `1e-4` -> `0.0001`,
  `1e-5` -> `1e-5`); `NaN` and `inf`/`-inf` are spelled like Rust.
- `f32` values are formatted from their own shortest representation.
- Debug String escaping: `"quote"`, backslash, `\n`, `\r`, `\t` and control
  bytes as `\u{XX}`; UTF-8 bytes pass through unchanged.
- Parsing: `ls_str_parse_i64` / `ls_str_parse_f64` consume the whole string,
  reject whitespace/underscores, return false on overflow; `parse_f64` accepts
  Rust's forms (`1.`, `.5`, `1e10`, `inf`, `NaN`).

## Panics and checked arithmetic

All panics print to stderr

    thread 'main' panicked at <file>:<line>:<col>:
    <message>

then flush stdout and stderr and call `exit(101)`. They never return.

| Helper | Message |
| --- | --- |
| `ls_panic_div_zero(file,line,col)` | `attempt to divide by zero` |
| `ls_div_<T>_checked` (divisor 0) | `attempt to divide by zero` |
| `ls_rem_<T>_checked` (divisor 0) | `attempt to calculate the remainder with a divisor of zero` |
| `ls_panic_overflow(file,line,col,op)` | `attempt to <op> with overflow` (`add`, `subtract`, `multiply`, `divide`, `negate`, `shift left`, `shift right`) |
| `ls_panic_bounds(file,line,col,len,index)` | `index out of bounds: the len is <len> but the index is <index>` |
| `ls_panic_at` / `ls_panic_cstr` | user message |

Checked arithmetic helpers exist for every integer type (`ls_add_i8_checked`,
..., `ls_neg_i64_checked`, `ls_shl_u64_checked`, ...). They take the two
operands, then `file, line, col`, panic exactly like Rust, and are emitted only
in debug builds; release builds use wrapping operators. Divide/remainder by
zero panics in both configurations because generated code always calls the
checked helper for division.

## IO, process and math

Basic process helpers:

- `ls_runtime_init(argc, argv)`; `ls_args()` returns `LsVec_String` of the
  user arguments **excluding** the executable name. On Windows the runtime
  ignores the narrow C `argv[]` (MinGW encodes it in the ANSI code page) and
  rebuilds the argument vector from `GetCommandLineW()`, splitting it with the
  documented `CommandLineToArgvW` rules and converting every argument to UTF-8,
  so non-ASCII paths survive. Arguments are validated as UTF-8 on every platform.
- `ls_read_line()` returns `LsOpt_String`: `None` on EOF, otherwise the line
  with the trailing newline (and Windows `\r`) removed.
- `ls_read_file(path)` / `ls_write_file(path, contents)` return
  `LsRes_String_String`; errors carry the OS message as
  `"<strerror> (os error N)"`. Both are binary safe.
- `ls_exit(code)` flushes and exits with `code`.
- Math helpers: `ls_abs_*`/`ls_min_*`/`ls_max_*` for every integer type,
  plus `ls_abs_f32/f64`, `ls_min_f32/f64`, `ls_max_f32/f64`, `sqrt`, `pow`,
  `floor`, `ceil`, `round`, `sin`, `cos`, `tan`, `ln`, `log10`, `exp`.

Handle based I/O (`lsaca_rt_io.c`, declared in `lsaca_rt.h`):

- Handles are `int64_t` indices into a dynamically grown table (64 slots
  initially, shared by files and sockets). `ls_io_stdin/stdout/stderr` are the
  fixed handles 0/1/2; closing them fails. Invalid or closed handles return -1
  with `INVALID_INPUT`.
- Files: `ls_io_open` (read-only), `ls_io_create` (create/truncate write),
  `ls_io_close`, `ls_io_read`, `ls_io_write`, `ls_io_seek` (whence 0/1/2),
  `ls_io_flush`, `ls_io_size`, `ls_io_set_nonblocking`. Read returns 0 at EOF;
  write returns the byte count.
- Errors are per-thread: every public call resets them, `ls_io_last_error_kind()`
  returns an `LsIoErrorKind` (0 none, 1 not_found, 2 permission_denied,
  3 already_exists, 4 invalid_input, 5 connection_refused, 6 connection_reset,
  7 connection_aborted, 8 timed_out, 9 would_block, 10 interrupted,
  11 unexpected_eof, 12 unsupported, 13 address_in_use, 14 address_not_available,
  15 broken_pipe, 16 other) and `ls_io_last_error_message()` returns a fresh
  owned String with the OS message, `"<message> (os error N)"`.
- Directories and paths: `ls_io_read_dir` returns an owned `Vec<String>` of
  entry names (sorted, `.`/`..` skipped), `ls_io_metadata(path, &size, &mtime_ms,
  &kind)` reports kind 0 file / 1 directory / 2 other, and
  `ls_io_create_dir`/`create_dir_all`/`remove_file`/`remove_dir`/
  `remove_dir_all` (iterative walk, no recursion depth limit)/
  `ls_io_rename`/`ls_io_canonicalize`/`ls_io_current_dir`/
  `ls_io_set_current_dir`/`ls_io_temp_dir` cover the usual filesystem work.
- TCP over IPv4/IPv6: `ls_net_listen("host:port")` (port 0 picks a free port),
  `ls_net_local_port`, `ls_net_accept` (would_block when nonblocking),
  `ls_net_connect`, `ls_net_set_timeout` (receive/send milliseconds) and
  `ls_net_shutdown` (0 read, 1 write, 2 both). Reads and writes use the same
  `ls_io_read`/`ls_io_write` handle calls.
- Time: `ls_time_now_ms`, `ls_time_monotonic_ns`, `ls_time_sleep_ms`,
  `ls_time_local_parts`/`ls_time_utc_parts` (calendar breakdown in the local
  timezone or UTC, out parameters may be NULL).
- Environment: `ls_env_var` returns NULL when the variable is unset,
  `ls_env_vars` returns an owned sorted `Vec<String>` of `KEY=VALUE` entries,
  `ls_proc_args` returns the owned argument vector.
- Every returned `LsString*`/`LsVec_String*` is a fresh owned reference
  counted value (except `ls_env_var` NULL); release it with `ls_release()`.
- All file, directory and socket calls are platform backed: Win32 wide APIs on
  Windows (UTF-8 paths are converted to UTF-16, >2 GiB files and long paths are
  supported through the wide interfaces), POSIX.1-2008 on Linux/macOS. The TCP
  API needs `ws2_32` on Windows.

## Leak reporting

When the runtime is compiled with `LSACA_DEBUG` or `LSACA_DEBUG_RC`,
`ls_runtime_shutdown()` runs pending collections and then walks the live-object
list. If anything is still alive it prints to stderr:

    lsaca: warning: 3 reference-counted allocation(s) leaked
    lsaca:   leaked allocation of 10 bytes
    ...

Up to eight allocations are listed (most recently allocated first). A correct
program prints nothing, also in debug builds; release builds do not track
allocations at all. The runtime self-test uses this mode to prove that the
whole suite leaks nothing.

The suite is also a bounded stress test: the collector cases build 5000 small
cycles, a 2000-node ring, and live roots pointing into garbage cycles, then
release 100000 managed objects in deterministic PRNG order with periodic
collection; the hash-map cases drive 100000 i64 keys and 20000 String keys
through insert/lookup/remove/reinsert and three clear/refill grow cycles, plus
hand-built adversarial table states that force the defensive probe outcomes.
All of that runs in well under a second in the release configuration.

Windows smoke matrix (release/debug/leak-tracking builds of the runtime and
the I/O suite, then the panic/leak/IO/stdin/args child processes; ends with

## Portability notes

- C17 only; `max_align_t`, `stdint.h`, `stdbool.h`, `<math.h>`, `<stdio.h>`.
- Windows: stdout/stderr are switched to binary mode so program output is
  LF-only (matching Rust); file, directory and socket I/O uses Win32 (wide
  UTF-16 APIs) and Winsock2, so UTF-8 paths and non-ASCII arguments work;
  link with `-lws2_32`. POSIX builds use POSIX.1-2008 (`_POSIX_C_SOURCE
  200809L`, `_DEFAULT_SOURCE` on Linux, `_DARWIN_C_SOURCE` on macOS).
- No hidden global state besides the stored (UTF-8) argument vector, the I/O
  handle table, the `WSAStartup` state on Windows and (in tracking builds) the
  intrusive debug list of live allocations.
- No threads, no signals; everything is deterministic.
